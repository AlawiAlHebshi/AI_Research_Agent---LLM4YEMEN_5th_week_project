# ذاكرة البحث المستمرة — المرحلة الأولى

تُحفظ الأبحاث التي اجتازت التحقق تلقائيًا بعد انتهائها في SQLite، دون تنزيل
حزم إضافية. تستعمل الوحدة `memory.py` مكتبة `sqlite3` المدمجة في Python.
لا تُستورد الأبحاث القديمة من JSONL تلقائيًا، ولا تُضاف بيانات الاختبارات إلى
قاعدة المستخدم. تبقى القاعدة الجديدة فارغة إلى أن ينتهي بحث متحقق أو يُدرج
سجل اختبار في قاعدة الاختبار المنفصلة.

## أين تُحفظ البيانات؟

المسار الافتراضي، محسوبًا من مجلد المشروع:

```text
.runtime/memory/research.sqlite3
```

يمكن اختيار مسار آخر بواسطة `--memory-db` أو متغير العملية
`RESEARCH_MEMORY_DB`؛ أولوية وسيطة CLI أعلى من المتغير. المسار النسبي محسوب
من جذر المشروع. يجب أن يبقى المسار داخل `.runtime/` وبامتداد `.sqlite3` أو
`.sqlite` أو `.db`. تُرفض الروابط الرمزية وWindows junctions، بما فيها ملفات
SQLite الجانبية. لا تُقبل `usage.json` أو `.env` أو مسارات `reports/`.
يمكن لاحقًا تركيب تخزين دائم في هذا المجلد عند النشر؛ إعداد النشر غير منفذ هنا.

أوامر الذاكرة لا تحمّل `.env` ولا تستدعي OpenAI أو أدوات البحث. إذا أردت تغيير
المسار لها فاستعمل وسيطة CLI أو متغير العملية، وليس ملف إعدادات الأسرار.

```powershell
.\.venv\Scripts\python.exe -B main.py --memory-init
.\.venv\Scripts\python.exe -B main.py --memory-list --memory-limit 5
.\.venv\Scripts\python.exe -B main.py --memory-search "RAG" --memory-limit 5
```

بعد بحث جديد مقبول يعرض CLI `معرّف البحث` و`حالة الذاكرة`. انسخ المعرّف إلى:

```powershell
.\.venv\Scripts\python.exe -B main.py --memory-get "PUT_RESEARCH_ID_HERE"
```

استبدل `PUT_RESEARCH_ID_HERE` بمعرّف حقيقي؛ ليس هذا أمرًا لإجراء بحث جديد.
لإظهار النتائج عبر مسار مخصص:

```powershell
.\.venv\Scripts\python.exe -B main.py --memory-db ".runtime/memory/custom.sqlite3" --memory-init
.\.venv\Scripts\python.exe -B main.py --memory-db ".runtime/memory/custom.sqlite3" --memory-list
```

المعرّف غير الصحيح يرجع خطأ آمنًا. المعرّف الصحيح غير الموجود أو القاعدة
غير المنشأة يرجعان نتيجة فارغة ورسالة توضيحية دون إنشاء قاعدة بسبب القراءة.
`--memory-init` ينشئ القاعدة صراحةً. لا يمكن جمع أمر ذاكرة مع `--query` أو
`--save`. البحث الجديد المعتاد يسجل الذاكرة تلقائيًا؛ تشغيله قد يكلّف API،
ولذلك لم يُستخدم ضمن اختبارات هذه المرحلة.

## بنية قاعدة البيانات

جدول واحد `research_records`:

| العمود | المحتوى |
|---|---|
| `owner_id` | نطاق مالك يحدده التطبيق؛ الافتراضي `local` |
| `task_id` | UUID المهمة، وهو معرّف JSONL نفسه في مسار CLI |
| `question` | السؤال الأصلي بعد تنقية محارف التحكم وأنماط الأسرار المعروفة |
| `topic` | عنوان البحث المتحقق |
| `mode` | `web` أو `scientific` |
| `summary` | الملخص النهائي المتحقق، بما فيه حدود النتيجة المعلنة |
| `sources_json` | قائمة مرتبة بالمراجع: الرابط والعنوان والمؤلفون والسنة وDOI وarXiv ونوع المنشور حسب المتاح |
| `status` | `success` أو `degraded` فقط |
| `created_at` | تاريخ إنشاء السجل بصيغة ISO 8601 وUTC |
| `tools_used_json` | أسماء الأدوات الفعلية |
| `search_text` | السؤال والعنوان بصيغة موحدة للبحث النصي |

المفتاح الأساسي `(owner_id, task_id)` يمنع تكرار المهمة في نطاق المالك، دون
استبدال السجل الموجود. يتوحّد شكل UUID سواء كُتب بشرطات أو دونها. يوجد فهرس
`research_date` على المالك والتاريخ. يميز `application_id` القاعدة، و`user_version=1`
نسخة البنية؛ تُرفض قواعد التطبيقات الأخرى والإصدارات غير المدعومة دون ترحيلها.

لا توجد جداول مالية، ولا تخزين مفاتيح أو ترويسات اتصال أو استجابات مزود خام.
تستبعد `.gitignore` قواعد البيانات وملفات journal/WAL/SHM.

## متى وكيف يُحفظ البحث؟

1. يسترجع التطبيق، عند توفرها، حتى ثلاثة مقتطفات تاريخية مرتبطة بكلمات السؤال
   وفي النمط نفسه، ويضعها في `context.previous_research`.
2. ينفذ الوكيل البحث المعتاد ويطبق التحقق الحالي دون تعديل تعليماته أو قواعد مصادره.
3. إذا كانت النتيجة `success` أو `degraded` تُنشأ لقطة بالحقول المحددة فقط،
   مع التأكد مجددًا أن روابطها ضمن أدلة المهمة وأن الأوراق العلمية لها ملخص.
4. يُدرج السجل داخل معاملة SQLite. إعادة إدراج المهمة نفسها لا تستبدل محتواها.
5. تظهر حالة `saved` أو `already_exists` أو `failed` في CLI. إذا تعذر التخزين،
   تبقى الإجابة المتحققة مع تحذير، ولا يدعي التطبيق أنها حُفظت في الذاكرة.

الأجوبة الفاشلة أو غير المتحققة لا تُسجل كأبحاث مكتملة. أعطال استرجاع الذاكرة
لا تمنع البحث الجديد؛ تُذكر في تحذير. تُسجل أحداث `memory_loaded`, `memory_saved`,
`memory_error` داخل آثار البحث، دون نسخ المحتوى أو مسار القاعدة إليها.

في الاستخدام البرمجي المباشر، فعّل التخزين بتمرير `memory=ResearchMemory(...)`
إلى `run_research`، مع `task_id` عند توفره. الاستدعاء البرمجي دون هذه الوسيطة
يبقى بلا تخزين ضمني؛ مسار CLI يمرر المكوّن تلقائيًا.

## الفصل بين الذاكرة والتقارير والأدلة

- التخزين الداخلي تلقائي؛ حفظ `.txt` في `reports/` يبقى بحاجة إلى تأكيد المستخدم.
- الرفض أو الإلغاء عند حفظ تقرير لا يمسح لقطة البحث السابقة.
- يُعرض المسترجع بوصفه `previous_research`, `untrusted_data=true`, `fresh_evidence=false`.
- وفق اختيار المستخدم لهذه المرحلة، لا تُرسل الذاكرة إلى LLM ولا تُضاف إلى
  التعليمات أو رسائل البحث أو `context.sources`. المراجع التاريخية لا تصبح
  أدلة جديدة ولا تنقذ مهمة لم تسترجع أدلة حديثة.
- يحتوي المقتطف التاريخي على المعرّف والتاريخ والنمط وعنوان حتى 200 حرف، وسؤال
  حتى 300 حرف، ومقتطف ملخص حتى 600 حرف. عدد المقتطفات لا يتجاوز ثلاثة.
- استعراض CLI يعيد السجلات الأصلية كاملة ضمن حد 1–10 سجلات، افتراضيًا خمسة.
  البحث نصي بسيط في السؤال والعنوان، وليس بحثًا دلاليًا أو متجهيًا.

كل الاستعلامات تستخدم معاملات SQL مربوطة. التعليمات الخبيثة المخزنة مجرد نص
ولا تُنفذ. تُنقّى أنماط الأسرار المعروفة وتُرفض الروابط الحاملة لمعاملات اعتماد
معروفة؛ لا يُعد ذلك ضمانًا لكشف كل سر يمكن أن يكتبه المستخدم بصيغة غير معروفة.
قاعدة البيانات غير مشفرة؛ يلزم ضبط صلاحيات نظام الملفات والاحتفاظ بالبيانات لاحقًا.

كل قراءة وكتابة مقيّدة بـ`owner_id` تمهيدًا للمستقبل، لكن هذا **ليس تسجيل دخول
ولا عزلًا آمنًا بين المستخدمين**. لا يقدم CLI اختيار مالك. قبل النشر المتعدد
المستخدمين يلزم ربط النطاق بهوية موثقة وضبط الوصول إلى الملف والخدمة.

## الاختبارات المحلية

```powershell
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p test_memory.py -v
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -q
```

تختبر المجموعة الحفظ والاسترجاع بالعربية والإنجليزية، والفتح مجددًا ومن عملية
Python جديدة، ومنع التكرار، والسجلات غير الصالحة، والقاعدة المفقودة والتالفة
وغير المتاحة، وعدم ترحيل قاعدة أخرى، ونطاق المالك وحدود الاسترجاع، وحقن SQL
ونصوص التعليمات المخزنة، وعدم تمريرها للنموذج، وفصل الحفظ عن إذن التقارير،
والبحث العلمي وميزانية التطبيق. بياناتها اصطناعية معلّمة داخل `.runtime/tests/`؛
لا تدخل قاعدة المستخدم الافتراضية ولا تُعرض كأبحاث حية.

### النتيجة المتحققة — 5 نوفمبر 2026

- نجح اختبار الذاكرة الـ22 ونجحت المجموعة الكاملة: **166 اختبارًا**.
- اختُبرت أوامر `--memory-init`, `--memory-list`, `--memory-search`, `--memory-get`
  فعليًا دون نموذج، وأُنشئت القاعدة الافتراضية فارغة. SQLite المحلية: `3.50.4`.
- اختُبر استمرار سجل اصطناعي من عملية Python جديدة داخل قاعدة اختبار منفصلة.
- تطابقت بصمة SHA-256 لسجل `.runtime/usage.json` قبل أوامر CLI وبعدها.
- تأكد استبعاد قاعدة البيانات من Git. لم تُثبّت حزم ولم تُنفذ طلبات OpenAI مدفوعة.

## ما بقي للواجهة؟

لم تتغير Streamlit. يلزم لاحقًا محوّل يحوّل `ResearchRecord` إلى بيانات العرض،
ويصل سجل الجلسة بقائمة SQLite والتفاصيل عبر المعرّف، ويعرض تاريخ البحث وحالته
وسياقه التاريخي، مع الحفاظ على تأكيد حفظ الملفات. لا تُرسل ذاكرة المستخدم
إلى النموذج دون قرار مستقل. الذاكرة لا تصلح أعطال مزودي البحث أو نقص الأدلة.
